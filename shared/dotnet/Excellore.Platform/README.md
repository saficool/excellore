# Excellore.Platform

`TenantUnitOfWork<TDbContext>` runs database work in a transaction. It reads the tenant ID from the scoped `ITenantIdAccessor`, executes parameterized `SELECT set_config('app.tenant_id', ..., true)` as the first statement inside the transaction, then runs the work, saves changes, and commits. It rejects a missing tenant or a scope change before commit. Failed work rolls back when the transaction is disposed.

Register `AddExcelloreAuthz()` in the API so `ITenantIdAccessor` resolves to the same scoped tenant context opened by the tenant gate. Worker hosts call `AddExcelloreWorkerTenantScope()` and run each job with `TenantWorkerScope.RunAsync<TJob, TResult>(tenantId, work)`. It binds the tenant before resolving the scoped job and disposes the scope afterward. The host uses a machine identity; the job rechecks resource ownership inside tenant context. Do not register both HTTP and worker tenant accessors in one host. Use the same `DbContext` instance in the work delegate; never issue tenant database commands outside this boundary. See proposed ADR-0010 and ADR-0013.

The transaction tests use SQLite to verify statement order, commit, rollback, and scope checks.

`TenantDbContext` provides the EF defense in depth for class T entities. Map only `ITenantOwnedEntity` classes in a derived context; its sealed model-building step applies a filter using the current scoped tenant for every mapped class T entity. It rejects unsupported entity types and preexisting filters so a tenant filter is never silently omitted or overwritten. Synchronous and asynchronous `SaveChanges` stamp an empty `TenantId` on new rows and reject writes whose current or original tenant differs. Class P and H tables require separate, explicit context designs. This EF filter supplements PostgreSQL forced RLS; it does not replace it. See proposed ADR-0011.

The PostgreSQL RLS checks and a Testcontainers fixture are in `Excellore.Platform.Testing` (proposed ADR-0012). Each service must run the checks against its own migrations and restricted runtime role before exposing tenant tables.

`IEventBus` exposes a service-queue subscription and `CreatePublisherAsync` for platform events. `RabbitMqEventBus` uses the `excellore.events` topic exchange, a durable quorum queue per service, manual acknowledgement after handler success, two bounded retries, and a dead-letter queue for poison or oversized deliveries. Give it a broker URI from configuration and one dictionary of event-type handlers per service queue. Dispose subscriptions and publishers on shutdown. The publisher uses tracked broker confirmations, persistent messages, and mandatory routing. See proposed ADR-0015 and ADR-0019.

`PostgresEventInbox.RunOnceAsync(connection, eventId, tenantId, work)` starts a transaction, sets the tenant context locally, claims the event ID in the service's class P `inbox` table, and commits the marker with the handler's database changes. It returns `false` for a duplicate. The callback must use the supplied transaction; send external effects through an outbox. Pass `null` only for a global event after validating its envelope. Each service creates and grants its own `inbox` table in its migration; the shared library never creates it at runtime. See proposed ADR-0016.

`PostgresEventOutbox.EnqueueAsync(transaction, eventId, eventType, tenantId, payload)` writes an event to the caller's active PostgreSQL transaction. Commit the state change and event together; pass a null tenant only for a global event. It checks the envelope metadata against the row, but the producer must still validate its event schema and exclude secrets and personal data. Each service migration creates its own class P `outbox` table and adds the required RLS exemption entry. See accepted ADR-0018.

`PostgresOutboxDispatcher.DispatchOnceAsync(connection, publisher)` locks one pending row, revalidates its envelope metadata, publishes it, and marks it sent only after broker confirmation. Call repeatedly from a service worker with a dedicated database role that can read rows and update only `published_at`. A failed or uncertain publication leaves the row pending for retry; duplicates are possible and consumers use their inbox. Service hosts own the polling loop and lifecycle. See proposed ADR-0019.

For API health probes, call `AddExcelloreHealthChecks()` and register the host's dependency checks on the returned builder, then call `MapExcelloreHealthChecks()`. `/health/live` reports process liveness without running dependencies. `/health/ready` runs all registered checks and returns `503` for degraded or unhealthy results. Responses contain only the overall status, never check descriptions or exceptions. Route these endpoints only on an internal network path; each service must register the dependencies it needs before accepting traffic.
